# 背景

这是产品的入口动作。原 PRD 要求"用户拍 3~5 张，AI 跨图识别并推断库存增减，默认零点击"。
没有规格时最容易做错的事：逐项让用户确认、拍到一半丢图、拍漏一层就误删。

## 目标

- 3 个视角拍完 → 15 秒内出现零点击摘要卡
- 没拍到的食材不会立即消失（连续 2 次降 `probably_removed`，3 次才 `removed`）
- 一次失败（解析/超时）不留下半条库存记录
- 图片不落任何服务器存储

## 用户故事

作为用户，我对着冰箱拍三张就能知道"今天多了什么、快过期什么"，不需要逐项勾选；
拍漏了一层，下次再拍也不会有东西凭空消失。

## 范围

**做**：三视角引导、逐张压缩、Base64 上传、云函数识别与状态机、摘要卡、库存列表展示。

**不做**：条码扫描、超过 3 个视角的引导、历史照片回看、并发多设备共享。

## 交互与规则

1. 进入 `pages/capture`，顶部固定显示当前视角（正面全景 → 上层 → 下层）。没有"随便拍"入口。
2. 每拍一张：`wx.chooseMedia`（camera）→ 压缩（quality 0.7，长边 1280）→ 读 Base64 → 删除临时文件。
3. 最多 8 张（产品只用 3 张），超出由 `prepareImages` 在压缩前拦截。
4. 三张齐了才出现"识别入库"；可重拍最后一张。
5. 云函数返回后展示摘要卡：✅ 新增 / 🔄 数量可能变化 / ❓ 似乎已取出；只有带 `questionId` 的行有按钮。
6. 失败路径：Key 未配置 → 引导去设置页；超时/解析失败 → 提示重试，**不写库存**。

## 验收标准

- [x] AC1 超过 8 张在压缩前拦截（`test/utils.test.js` → `prepareImages：超过 8 张直接拦，不浪费压缩开销`）
- [x] AC2 逐张串行压缩，读完立即删临时文件（`prepareImages：逐张串行，压完读完立即删临时文件`）
- [x] AC3 压缩参数不支持时降级为只传 quality（`压缩参数被拒时退回只传 quality`）
- [x] AC4 单张过大降质重压一次（`单张过大时降质重压一次`）
- [x] AC5 三视角依次引导，拍完不可再加（`capture：三视角依次引导，拍完 done`、`引导拍完即不可再加`）
- [x] AC6 低置信不建实体、不污染库存（`test/inventory-engine.test.js` → `低置信只进待整理，不匹配也不创造实体`）
- [x] AC7 未观测 2/3 次才降级（`连续未观测：2 次降 probably_removed，3 次才 removed`）
- [x] AC8 同轮重复标签只建一条（`同一轮里重复标签只建一条`）
- [x] AC9 解析失败不写半成品（代码审阅：`cloudfunctions/aiProxy/index.js` 先 `fail('E_PARSE')` 再落库，无事务外写入）
- [ ] AC10 真机半小时内 3 张图 ≤15 秒（人工，待验证）

## 数据契约

写 `observations`（先写）+ `inventory_items`（只写 `changed`）；接口见 `docs/api/cloud-functions.md` 的 `inventory.scan`。

## 风险与未决

- 真机拍摄构图质量决定识别率，尚无真机数据；AC10 验证时同时记录识别率。
- 云函数超时依赖控制台配置，属于部署风险，见 `docs/ops/deploy.md`。
